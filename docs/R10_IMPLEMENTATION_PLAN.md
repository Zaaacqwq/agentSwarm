# R10 实施方案：简化工作流

> 依据：
> - R9 验收时的 AGE-1：6 行改动，用了 69 分钟、$1.09、7 个 Agent，要你出手 5 次；
> - 对 agent-swarm-ng、Ateam、Vibe Kanban、Conductor、Codex App、Kiro / Spec Kit 的调研（2026-10-19）；
> - 你提出的三种情况：新项目立项、旧项目修 bug、临时小测试。
>
> 你同意了第 9 节的全部推荐（"按推荐"，2026-10-19）。原来的 R10"本地模型"顺延为 R11。

## 0. 本阶段解决什么

现在每张工单都走一条很长的固定流水线：需求确认 → 调研 → 讨论 → 写方案 → 等你批准 → 构建 → 验证 → 等你合并 → 复盘。小改动也一样，AGE-1 就是例子：
- **调研和讨论**：派了 2 个调研员，再回头问你 3 个问题；
- **QA 做了两遍**：构建阶段和验证阶段各一次，你也被问了两次要不要批准桌面；
- **QA 的报告也被审查**：两个 QA 都没改代码，还是各派了一个审查员；
- **lead 不信 QA 的截图**：自己写脚本分析像素，最后停在半路；
- **你出手 5 次**。

调研的工具里，Ateam、Vibe Kanban、Conductor、Codex App 和 agent-swarm-ng 的默认做法都是：
- **一个任务，一个 Agent，一个分支**，Agent 直接动手，不先调研、写方案；
- **卡住了就进"等你"**，做完进"审核"；
- **你看改动**：逐行评论，评论直接发回给 Agent 改（Vibe Kanban）；不满意可以作废，换个 Agent 或换个说法重来（Vibe Kanban）；
- **合并只靠一个按钮**（Ateam 走 `gh pr merge`），合并后卡片自动挪到"完成"。

只有大的、新的工作才值得先写规格（Kiro 和 Spec Kit 的做法：需求 → 设计 → 任务）。

R10 把工作流换成这个思路，同时保留它们没有、我们已经有的东西：
- 隔离的工作站和 Relay；
- 手机和 Discord；
- 模拟器、浏览器、桌面验收；
- 经验库和角色手册。

## 1. 验收（真实环境）

1. **改项目**：在一个已有项目上建一张小 bug 单，从 Todo 走到 PR，你只出手 1 次（看改动、点合并）。
   - 用时 15 分钟以内，花费 $0.40 以内，按 AGE-1 那样大小的改动计。
   - 在改动上逐行评论两处，点"发回修改"，lead 改完更新同一个 PR。
   - 点"重来"，换 Claude Code 重做一次，两次尝试都留在工单上。
2. **新项目**：一句话的想法 → 回答几个问题 → 批准一份方案 → 在本地仓库做出来、附截图 → 点"留下" → 自动建好 GitHub 私有仓库并登记为项目，项目档案也填好。
3. **小测试**：一张单子，没有关卡，做完直接给结果；7 天后本地仓库自动清理，除非你点了"留下"，那样就转成新项目。
4. **交文件、取结果**（2026-10-19 加入）：用一份真实的作业或测试文件（PDF、zip、代码），在手机上建一张小测试单并附上文件，或者从 Mac 上的收件箱里选；Agent 做完后，在手机上下载它产出的文件。
5. **工单依赖**（2026-10-19 加入）：B 被 A 挡住时，B 放进 Todo 也不会开工；A 完成后 B 自动开工。

## 2. 三种工单

新建工单时先选类型，只有三种：

| 类型 | 用在 | 你出手几次 |
|---|---|---|
| **改项目** | 已有项目里修 bug、加小功能、改文案 | 1 次：看改动、合并 |
| **新项目** | 从一个想法开始做一个新东西 | 2 次：批准方案；决定留下还是放弃 |
| **小测试** | 试一个想法、验证一个问题、查一件事 | 0 次；你想保留结果时再点"留下" |

现在的"功能""Bug"合并成"改项目"。"调研"改为小测试的一种：只出报告，不写代码。"营销"变成改项目的一个选项：勾上就由营销写手参与。"沙盒"加"立项"这条路，合并进新项目和小测试。

### 2.1 改项目

**默认直接做，没有固定阶段。** lead 拿到工单后：
1. 读工单和项目档案。不清楚就提问，卡片进"等你"；清楚就直接动手。
2. 自己改代码，按待办清单推进（借鉴 agent-swarm-ng：这一轮结束时清单没做完，就让它接着做）。只有能并行、互不相干的部分才派子 Agent。
3. **自动检查**：lead 说"做完了"之后，swarmd 在它的工作区里跑项目档案里的构建和测试命令。
   - 失败就把输出退回给 lead；
   - 连续 3 次同样的错，就停下来，卡片进"等你"，说明卡在哪。
4. **看界面**：改动会影响界面，而且验收标准需要亲眼看，才派**一个** QA，只验一次：iOS 用模拟器，网页用浏览器，Mac App 用桌面。
5. 开 PR，卡片进"审核"。

**什么时候先给你看方案：**
- 你建单时勾了"先给我看方案"；
- 或者 lead 判断风险大：改动很大、涉及数据迁移或安全，或者有几种做法需要你选。

这时它先写一份短方案，卡片进"等你"，你批准后再做。

### 2.2 新项目

用 Kiro 那样的轻量规格，只走一遍：
1. **问清楚**：lead 提几个问题，每个附上它的推荐。
2. **方案**：一份文档，写清需求（带验收标准）、设计（技术栈、结构）、任务拆分，你批准。
3. **做出来**：在本地仓库里做，用子 Agent 并行做各个部分，自动检查，最后附截图或演示。
4. **你决定**，三个按钮：
   - **留下**：建 GitHub 私有仓库，推上去，登记成项目，并按方案填好项目档案（平台、构建和测试命令、scheme）；
   - **再改**：写几句意见，发回给 lead 继续；
   - **放弃**：本地仓库删除。

### 2.3 小测试

保持现在沙盒的做法，再简化：
- 本地仓库，没有关卡，不开 PR，做完直接把结果写在工单上；
- 只想知道答案的话，勾"只调研"，就不写代码，只出一份带出处的报告；
- 7 天后自动清理；中途点"留下"，就进入新项目的"你决定"那一步。

## 3. 看板

借鉴 Ateam，卡片按 Agent 的状态自动移动：

| 列 | 什么时候在这里 |
|---|---|
| Backlog | 还没打算做 |
| Todo | 排队，有空位就开工 |
| 进行中 | Agent 在做 |
| **等你** | 它在提问、等你批准方案或桌面会话，或者卡住了 |
| **审核**（新增） | PR 开好了，等你看；小测试和新项目的结果也在这里 |
| 完成 | PR 合并后自动挪过来；或者你点了"留下"或"完成" |

取消的工单不显示在看板上，用筛选能找出来。

## 4. 工单页：看改动、评论、合并、重来

借鉴 Vibe Kanban 和 Ateam：
- **改动**：新加一个标签页，按文件列出这次改动，并排对比显示，手机上改为上下排列。数据来自 swarmd 的镜像仓库，不用去 GitHub 看。
- **逐行评论**：点某一行就能写评论。几条评论写完后点"发回修改"，合成一条消息发给 lead，卡片回到"进行中"，lead 改完推到同一个 PR。
- **合并**：一个按钮，点了要再确认一次，只有你能点。swarmd 用你的 GitHub 令牌合并 PR，合并后卡片自动进"完成"。在 GitHub 上合并效果一样。
- **重来**：作废这次尝试，删掉分支、关掉 PR，选另一种运行方式（原生、Claude Code、Codex）或另一个模型，可以再补一句说明，从头做一次。每次尝试都留在工单上，可以对比。
- **截图**：QA 的截图直接显示在工单上。lead 不必再验证截图真假，截图是 swarmd 自己截的（它的手册里写明这一点）。

## 4.1 交文件、取结果（2026-10-19 加入）

为了这类场景：你在外面，把作业或数据交给 Agent，再把结果拿回来。
- **附文件**：工单不再只能附图片，还能附 PDF、zip、代码、数据（CSV、JSON）、Notebook、文本。
  - 每个文件最多 25 MB，一张单子最多 10 个；
  - 文件放进工作区的 `inputs/` 目录；zip 由 swarmd 安全解压，路径不能越出这个目录，总大小也有上限；
  - 这些文件不会被提交进仓库，除非你勾选"跟文档一起提交"。
- **Mac 上的收件箱**：这台 Mac 上的 `~/agentSwarm-inbox` 文件夹，你在 Mac 上把下载的文件放进去，建单时从列表里选。swarmd 只读这个文件夹，Agent 仍然碰不到你家目录里的其他东西。
- **取结果**：小测试和新项目的 `outputs/` 目录，以及结果文档引用到的文件，都在工单页上列出来，可以一个个下载，也可以打包成 zip。手机上同样能下载。
- **作业**：Agent 帮你理解题目、搭环境、调试、检查你的解法。是否允许用 AI 做，取决于课程政策；系统不会、也没有能力代你提交到 LEARN。

## 4.2 工单依赖（2026-10-19 加入）

- 工单上可以写"被谁挡住"（可以有多个）；被挡住的工单放进 Todo 也不会开工，卡片上标出"被挡住"。
- 挡住它的工单全部完成后，它按优先级自动开工；如果挡住它的工单被取消了，提醒你决定怎么办。
- 不能形成循环（A 挡 B、B 又挡 A）。

## 5. 去掉的东西

- **调研和讨论这两个固定阶段**：调研只出现在新项目的方案里，或者"只调研"的小测试里。
- **构建阶段的 QA**：只在验证时做一次。
- **审查没改代码的运行**：QA、调研员不再配审查员；改了代码的子 Agent 照旧要审查。
- **每单都有的复盘阶段**：改成自动记录（用时、花费、出过的错）。只有出过问题才让 lead 写一条经验，比如重试过、被退回过、卡住过。
- **工单类型里的"功能""Bug""调研""营销""实验"**：见第 2 节。

## 6. 保留的东西

- 工作站隔离、Relay、只有你能合并到 `main`；
- 手机面板、Discord 提醒和按钮；
- 模拟器、浏览器、桌面验收，桌面会话仍然每次要你批准；
- 经验库和角色手册，复盘建议仍然要你采纳；
- 备用模型、researcher 的上限、预算上限。

## 7. 已有数据

- 进行中的旧工单照旧流程走完；新建的工单用新流程。
- 旧的类型对应到新类型：
  - 功能、Bug → 改项目；
  - 实验 → 小测试；
  - 调研 → 小测试（只调研）；
  - 营销 → 改项目（勾营销）。
- 数据库只增加字段，不删旧字段。

## 8. 实现顺序和测试

1. **流程**：
   - 三种类型的阶段和关卡；
   - lead 的简报和手册改成"直接做，必要时才提问、写方案"；
   - 待办清单，以及这一轮结束时的检查。
2. **自动检查**：构建和测试命令、失败退回、3 次停下。
3. **看板**：加"审核"列，卡片按状态自动移动。
4. **工单页**：改动对比、逐行评论和"发回修改"、合并按钮、重来和尝试记录。
5. **新项目和小测试**："留下 / 再改 / 放弃"三个按钮，7 天自动清理。
6. **去掉的东西**（第 5 节）。
7. **测试**：
   - **集成测试**，用脚本模拟模型：
     - 三种类型各走一遍；
     - 自动检查失败退回，3 次后停下；
     - 评论发回修改；重来；合并按钮；
     - 小测试转新项目；7 天清理；
     - 旧工单走完旧流程。
   - **E2E**：在手机宽度下看改动、逐行评论、合并、重来。
   - **真实验收**（第 1 节）。

## 9. 需要你决定的

1. **面板上加"合并"按钮吗？**（推荐加）
   - 点了要再确认，只有你能点，在手机上就能合并。
   - 不加的话，照旧去 GitHub 合并。
   - 如果 `main` 的保护规则要求审查，按钮会显示原因，你还是去 GitHub 合并。
2. **改项目什么时候先给你看方案？**（推荐：你勾选，或者 lead 判断风险大的时候）
   - 也可以选每次都要，那就和现在差不多，只是少了调研和讨论；
   - 或者从不，那就完全靠 PR 审核。
3. **新项目在 GitHub 上建成私有仓库吗？**（推荐私有）
4. **小测试 7 天后自动清理吗？**（推荐清理）
   - 清理前一天在 Discord 提醒你一次。
5. **"调研"和"营销"并进三种类型吗？**（推荐合并）
   - 新建工单的表单只剩三种类型。
6. **阶段编号：这次做 R10，"本地模型"顺延为 R11 吗？**（推荐）
