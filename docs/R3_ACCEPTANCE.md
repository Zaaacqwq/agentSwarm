几处值得记录的细节：
- **调研真的有用。** 调研 agent 在临时目录里装了 csv-parse 做实验，发现"同一个文件里混用 `\r\n` 和 `\n` 时会残留 `\r`"这个容易漏掉的坑，后来直接写进了实现和测试。
- **审查真的抓到了问题。** md-formatter 的审查 agent 自己写了一份参考实现，用 4000 组随机输入和它对比，找出表格宽度的计算方式前后不一致（遇到 emoji 这类字符时会对不齐），打回修改后重审才通过。
- **lead 的复盘基本准确**，它自己指出了 cli-dev 的任务说明写得太重。复盘里有一处说法不对：它说"本机 execFile 的 `input` 选项会让任何子进程挂起"。实际上 `input` 只对 `execFileSync` 和 `spawnSync` 有效，异步的 `execFile` 会忽略它，stdin 一直不关，子进程就会一直等。这是模型用错了 API，不是工作站环境的问题。
- **转义问题。** lead 在讨论阶段的总结里把 `<br>` 写成了 `&lt;br&gt;`，Discord 里显示的就是这串字符。这是模型自己的写法，swarmd 没有做任何转义；代码和 `plan.md` 里用的都是正确的 `<br>`。

## 验收中发现并修复的问题

1. **`report` 太长被拒后，模型原样重发了 16 次。** `report.summary` 的上限是 4000 字符，csv-spec-research 写了约 1 万字符，校验报错后它没有缩短，每次都带着整个上下文重发：这个子 agent 共读入 226 万 token，花了 $0.28，大部分发生在这十几次重发上。
   - **修复**：新增 `clipToSchema`，作为 Pi 的 `prepareArguments` 在校验前执行，把超长的文本截到上限，并在末尾标明截掉了多少字符。`report`，以及 lead 的 `tell_user`、`ask_user`、`stage_done`、`request_approval` 都使用它；`report.summary` 的上限同时放宽到 8000。
   - 有单元测试。
2. **40 回合对写 CLI 加集成测试的开发 agent 不够。** cli-dev 只跑了 3 分钟就到第 41 回合，大部分回合花在调试"连着终端时打印用法"的测试上，最后什么都没提交。lead 只好自己重写 C，结果 **C 没有经过审查 agent**，只经过了 QA 验证。
   - **修复**：默认回合上限从 40 改为 80，mission 的 lead 改为 150（它一次执行要跑完整个阶段：派生、等待、审查、合并）。每次执行 $1 的成本上限和 mission 总预算都不变。
3. **在最后一回合正常结束，仍被判成失败。** lead 在第 40 回合调用了 `stage_done`，返回成功，但同一时刻回合上限检查触发，把运行判为"用完回合上限"，任务卡住，直到你回复才继续。
   - **修复**：回合上限改在**下一回合开始前**检查，不再在回合结束时检查。最后一个允许的回合如果正常结束（`report` 或 `stage_done`），就不会被判失败。
   - 新增的集成测试在旧代码上失败，在新代码上通过。

以上修复验收结束后才合入；验收时运行的是 `929f067`。

## 代码审查

code-reviewer 报了 0 个 CRITICAL、2 个 HIGH、6 个 MEDIUM、7 个 LOW。

HIGH 全部修复，并且都有回归测试：
1. **停止 swarmd 会被当成取消任务**，进行中的 mission 会被取消，分支会被删除。现在停止属于中断：运行记为失败并附带"重启后继续"的提示，任务和分支都保留。
2. **`htmlToText` 的正则在恶意页面上要跑几分钟。** 现在改成线性扫描，20 万次重复的恶意输入也能在 1.5 秒内处理完。

MEDIUM：
- **已修复：**
  - 执行结束后才到的消息先存进数据库，不会丢；
  - Discord 发送失败或离线期间的消息，会在重连时和每 60 秒补发一次；
  - 清理只有在每一步都成功时才标记完成，失败会重试；运行还在收尾时不会清理；
  - 计划修改后，旧的 Approve 按钮会被拒绝；
  - Discord 客户端的启动和停止依次执行，连接不会重复，也不会泄漏。
- **只做了缓解：** 被网页诱导的 agent 仍然可能把仓库内容拼进 URL，借 `web_fetch` 泄露出去。现在查询参数限制在 512 字符以内，每个抓取过的 URL 都记在运行的时间线里。**不要让做调研的 agent 在含有密钥的仓库上工作。**

LOW：
- **已修复：**
  - 发审批消息前先检查是否允许进入下一阶段；
  - 收到新消息继续执行时，清除"等你回答"的状态；
  - `deleteBranch` 拒绝含 `..` 的分支名；
  - 在关卡处回复时，thread 里会附一条说明。
- **未修复：**
  - 工具列表在一次执行内不会变，阶段切换后要到下一次执行才更新；
  - 你要求修改后，`request_approval` 不检查 `plan.md` 是否真的改了；
  - 不属于 mission 的 R2 树，PR 被关闭时也会清理分支。这是按方案做的，但如果你关掉 PR 是想返工，分支就没了。

另外，审查期间发现一个 **R2 遗留 bug**：运行在释放工作站、刚进入等待状态的那一刻被取消，取消不会生效。已修复（`cancelTree`）。

## 剩余问题

- **网页工具的泄露风险**：见上文 MEDIUM 的最后一条。
- **lead 可以绕开审查。** 提示词允许 lead 自己完成小的工作包，这样的代码不经过审查 agent，只经过 QA。可以考虑让 lead 自己写的代码也必须经过一次审查。
- **调研最花钱**，占这次总花费的约一半。问题 1 修复后应该会明显下降，但还没有在真实运行里验证过。
- **R1 遗留分支**：`swarm/agentswarm-playground/fix-median-132912` 从来没开过 PR，监视器不会处理它，需要手动删除。
- **手机上的面板**：顶部导航被横向截断；改变窗口大小后，对话框没有停在最新消息。
- **Discord 里显示的是原文。** 模型写的 HTML 实体（如 `&lt;br&gt;`）会原样显示。
