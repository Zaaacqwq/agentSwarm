# R8 实施方案：营销与记忆（草案，2026-10-18）

> 依据：`PLAN.md` 第 4 节（营销、复盘）、第 11 节（记忆）、第 14 节，现有的复盘阶段，以及 agent-swarm-ng 的长期记忆（`docs/agent-memory.md`）。
> 第 7 节是需要你决定的事。

## 0. 本阶段解决什么

现在每张 ticket 都从零开始：
- **做完就忘**：上一个任务踩过的坑（比如 R5 验收时编不过 SwiftUI、lead 被模型提供方拒答、researcher 跑满时限），下一个任务的 Agent 完全不知道。复盘写完只存在那张 ticket 里，没人再看。
- **怎么做事写死在代码里**：各角色（lead、researcher、developer、reviewer、QA）的工作方法写死在代码的提示词里。你想调整，只能让我改代码。
- **只会写代码**：一个想法做成产品后，没人写落地页、App Store 文案和更新说明。

本阶段做完后：
- **经验库**：每次复盘，lead 把值得记住的教训记成几条"经验"，分属三个范围：全队、某个项目、某个角色。之后：
  - 新任务开工时，和这张 ticket 相关的几条经验会自动附在 lead 的第一条消息里；
  - 所有 Agent 都能用 `recall` 主动查；
  - 你置顶的几条，每个 Agent 一直都能看到。
- **角色手册**：每个角色一份 Markdown 写的工作方法，放进该角色的提示词。你在面板上直接改；Agent 在复盘时可以提修改建议，由你决定是否采纳。
- **营销**：
  - 新增 ticket 类型"营销"：给某个项目写定位、落地页文案、App Store 文案，配上从模拟器或浏览器截的图；
  - 项目可以设为"产品"：这样的项目里，功能 ticket 在开发的同时由 marketer 更新更新说明和商店文案，随 PR 一起交给你。

## 1. 验收（真实环境）

1. **一张 ticket 结束后，经验库里出现它的经验**：
   - 来源是那张 ticket，范围标明是全队、某个项目还是某个角色；
   - 在面板的"经验"页能看到，能编辑、置顶、停用。
2. **下一张相关的 ticket 用上了上次的经验**：
   - lead 的第一条消息里附着上次那几条经验；
   - 它的方案或做法里能看出照着做了，例如编 SwiftUI 项目时直接用 `sim_build`，而不是自己摸索；
   - 面板上能看到这条经验被用过几次。
3. **角色手册**：
   - 你在面板上改了 QA 的手册之后，下一个 QA 按新写法做；
   - 某次复盘里 Agent 提了一条手册修改建议，你在面板上点了采纳。
4. **营销**：
   - 一张"营销"ticket 给一个项目写出定位、落地页文案、App Store 文案，附截图，开成 PR 交给你；
   - 一个设为"产品"的项目，它的一张功能 ticket 的 PR 里同时带着更新说明。

## 2. 经验库

### 2.1 一条经验
- 一句话的标题（索引里显示的就是这句），加不超过 1000 字的正文。
- **范围**三选一：全队、某个项目、某个角色（例如 QA）。
- **来源**：哪张 ticket 的复盘，或者你自己写的。来源决定可信度：你写的是要求；Agent 写的是建议，不是命令。提示词里会标明这一点，防提示词注入。
- 还记录：用过几次、最后一次被用到是什么时候、是否置顶、是否停用。
- 你每次修改都保留旧版本。

### 2.2 怎么写进去
- **复盘阶段**：lead 多一个工具 `record_lesson`，每张 ticket 最多记 3 条。
  - 写之前先查有没有类似的：有就更新那一条，不重复记。
  - 只记可复用的做法和坑，不记这一次的流水账。
- **调研和实验 ticket**：它们没有复盘阶段，在最后一步也可以记。
- **你自己写**：在面板上直接新建，或者把某条复盘里的一句话"存为经验"。
- **长度和格式**：
  - 正文超过 1000 字会被拒绝；
  - 像密钥、令牌的内容一律拒绝保存。

### 2.3 怎么用
- **置顶**：最多 8 条，只有你能置顶。每个 Agent 的提示词里都有，适合"永远不要部署""betterUWWorks 的开发服务器用 3100 端口"这类事。
- **开工时自动附上**：
  - 用 ticket 的标题和描述去检索，在全队、本项目、lead 角色这三个范围里找最相关的 3 条，附在 lead 的第一条消息里，标明"以前的经验，供参考"。
  - 派生子 Agent 时，用它的任务说明再检索一次，附上本项目和它这个角色最相关的 2 条。
- **`recall({query})`**：所有原生 Agent 都有，主动查经验库。只返回它能看的范围，即全队、本项目、自己的角色。
- **Claude Code 和 Codex**：把置顶的和检索到的经验写进它们的任务说明里。
- **检索方式**：按关键词匹配，标题里的词权重更高，相同分数时新的优先。不调用模型，所以几乎不花钱、不费时间，和 agent-swarm-ng 的做法一样。以后接了本地模型可以再换成语义检索。

### 2.4 面板："经验"页
- 列表：按范围筛选，可以搜索；显示用过几次、来源 ticket、是不是 Agent 写的。
- 一条经验的详情：正文、来源、版本历史。可以编辑、置顶或取消置顶、停用或恢复。
- 停用的经验不再被检索到，但留着记录。

## 3. 角色手册

- **角色**：lead、researcher、architect、developer、reviewer、QA、marketer，每个一份 Markdown。初始内容从现在代码里写死的工作方法整理出来，行为不变。
- **放在哪**：手册放进对应角色 Agent 的系统提示词。一份手册不超过 4000 字，保持提示词稳定，便于缓存。
- **你改**：在面板的"手册"页直接编辑，保留每个版本，可以回到旧版本。
- **Agent 提建议**：复盘时 lead 可以用 `propose_handbook_change({role, change, why})` 提修改建议，每张 ticket 最多 2 条。
  - 建议出现在"手册"页，带来源 ticket。
  - 你采纳、编辑后采纳，或者驳回。手册是指令，所以不自动生效。
- **项目自己的做法**：仍然写在项目档案里（R5），不放进角色手册。

## 4. 营销

### 4.1 "营销"ticket
- **新的 ticket 类型**，只用于已有的项目。流程是：
  1. 调研：竞品、目标用户、卖点；
  2. 起草；
  3. 截图；
  4. 你审稿：批准，或者提修改意见；
  5. 开 PR；
  6. 你合并；
  7. 完成。
- **产出**放在 `docs/agentswarm/<任务>/marketing/`：
  - `positioning.md`：一句话定位、目标用户、和竞品比的卖点；
  - `landing.md`：落地页文案，包括标题、小标题、三到五个功能段落和行动按钮；
  - `appstore.md`（iOS 项目）：名称、副标题、描述、关键词、更新说明，按 App Store 的字数限制写；
  - `screenshots/`：由 QA 用模拟器或浏览器截取。
- **marketer** 是一个原生 Agent，有搜索网页和抓取网页的工具（R3）。按角色手册写。不改代码。

### 4.2 "产品"项目
- 项目档案里加一个开关：**这是一个产品**（默认关）。
- 打开后，这个项目的功能 ticket 在方案被批准后，lead 除了派 developer，还会同时派一个 marketer：
  - 更新这次改动的更新说明（`docs/agentswarm/CHANGELOG.md`，每次改动加一段）；
  - 必要时更新商店文案；
  - 这些随同一个 PR 交给你。
- bug ticket 只写一句更新说明，不派 marketer。

## 5. 复盘的改进

- **复盘的写法**：从"写一段总结"改成三步：
  1. 简短总结；
  2. 用 `record_lesson` 记最多 3 条经验；
  3. 可选：用 `propose_handbook_change` 提手册修改建议。
- **复盘时 lead 能看到的事实**（swarmd 自动整理给它）：
  - 用时、费用；
  - 被打回了几次、失败的子 Agent 和原因；
  - 模型请求出错的次数。

  这样经验基于事实，不靠印象。
- **调研和实验 ticket**：在最后一步也能记经验。

## 6. 实现顺序和测试

1. **数据**：
   - `lessons` 表和 `lesson_versions` 表；
   - `handbooks` 表和 `handbook_versions` 表；
   - `handbook_proposals` 表；
   - 项目档案加 `product` 开关；
   - ticket 类型加"营销"。
2. **经验库**：
   - LessonService：新建、更新、去重、检索、置顶、停用、使用次数；
   - 拒绝像密钥的内容。
3. **接进 Agent**：
   - 提示词里加入置顶的经验和角色手册；
   - 开工和派生时自动附上相关经验；
   - `recall` 工具；
   - CLI 的任务说明里也带上。
4. **复盘**：
   - `record_lesson`、`propose_handbook_change` 两个工具；
   - 复盘时的事实汇总；
   - 调研和实验的最后一步也能记经验。
5. **角色手册**：
   - 把现有的工作方法整理成初始手册；
   - 编辑、版本、采纳建议。
6. **营销**：
   - "营销"ticket 的流程和工作说明；
   - "产品"项目里的 marketer；
   - 商店文案的字数检查。
7. **面板**：经验页、手册页、项目档案里的"产品"开关、新建 ticket 时可以选"营销"。
8. **测试**：
   - 单元测试：检索的打分、去重、像密钥的内容、手册版本；
   - 集成测试：
     - 复盘记下经验，下一个任务开工时附上它；
     - `recall` 只返回能看的范围；
     - 采纳手册建议后，下一个对应角色的 Agent 的提示词里带着新写法；
     - 营销 ticket 走完全流程；
     - 产品项目的功能 ticket 带着更新说明；
   - E2E：经验页、手册页（编辑、采纳建议），375 和 1440 宽度；
   - 真实验收：第 1 节；
   - code-reviewer 和 security-reviewer 审查（Agent 写的文字会进入别的 Agent 的提示词）。

不在本阶段：
- 每个 Agent 自己的长期记忆和"夜间整理"：我们的 Agent 大多只活一张 ticket，记忆放在团队和项目层更有用；
- 语义检索：等 R10 有本地模型再说；
- 自动发布落地页或提交 App Store：只写文案，你来发；
- 设计稿和图标。

## 7. 需要你决定的

1. **Agent 记的经验是马上生效（不置顶、标明是 Agent 写的，你可以随时停用），还是每条都要你先批准？**（推荐马上生效）每条都批准，经验库很难攒起来；何况这些经验只作为参考附上，置顶只有你能做。
2. **角色手册：Agent 只能提建议、由你采纳，还是允许它直接改？**（推荐只能提建议）手册是每个 Agent 都要照做的指令，改错了影响面大。
3. **营销做哪些？**（推荐两样都做）
   - 一是"营销"ticket 类型；
   - 二是"产品"项目的功能 ticket 自动带更新说明。

   如果只要第一样，工作量小一些。
4. **经验的范围分三层：全队、项目、角色。**（推荐）也可以只分全队和项目两层，那样手册以外的角色经验就没地方放。
5. **检索先用关键词匹配，不用语义检索。**（推荐）关键词匹配不花钱、不费时间，每次开工都能用；语义检索要额外调用模型，留到 R10 有本地模型时再做。
