# P3 实施方案：多 Agent 与群聊（已确认，2026-10-09）

基于 P2（PR #2）。对应 `HIVE_PLAN.md` 第 12 节 P3：

- 群聊、Agent 之间私聊、@ 提及唤醒、防刷屏规则、回复与反应、成员管理；频道文件推到 P4；
- 调度器：多 Agent 并发回合、资源排队、在界面上能看到排队和等待状态；
- 前端：群聊界面、Agent 间会话（人只能读）、完善活动检查器、Portal 搜索。

不做：任务看板与交接（P4）、频道文件（P4）、打断当前回合的判断（plan 4.2 定为后期）、Agent 自建群（需要审批流程，放到后面）。

参考了 ASNG 的 `chat-and-groups.md`、`agent-communication.md`、`message-interruption.md`，下面注明哪些照搬、哪些按我们的计划调整。

## 0. 已确认的设计决定

1. **Agent 之间私聊**：被授予 `core.colleagues` 的 Agent 可以私聊同组织内的任何 Agent，不需要人逐对建立连接。等 P6 支持多用户后再收紧。
2. **频道文件推到 P4**：人上传附件、Agent 的 `attach_file`、文件抽屉，都在 P4 做任务交接时一起实现。
3. **默认数值**：
   - 群里只唤醒被 @ 的 Agent，`@all` 唤醒全部成员；
   - 会话链预算：人发起的 32 条，Agent 发起的 8 条；
   - 每个 Agent 每小时最多 60 条消息；
   - 收到消息后静默 1.5 秒再开回合。

## 1. 会话与上下文

- **每个 Agent 仍只有一个 Pi 会话**，私聊、群聊、Agent 私聊共用（同 ASNG）。Agent 有连续的身份，不会每个频道各一份记忆。每条输入都带服务端生成的来源头：频道、类型、发送者，以及发送者是人还是 Agent。
- **Agent 发来的内容不带主人权限**。别的 Agent 写的话只当任务资料，不能改变权限。只有调用发布工具才会对外发言。
- **回复地址由服务端决定**。只由 Agent 消息触发的回合，不能往人和 Agent 的私聊里发消息。这是为了防止 Agent 冒充主人交代的事。
- **多用户隔离留到 P6**。P1 审查已经指出：一个 Agent 一个会话，在多用户场景下会串话，要到 P6 做多用户时再处理（每人单独会话，或者限制 `read_channel` 的范围）。

## 2. 频道与权限

| 类型 | 成员 | 谁能写 | 唤醒规则 |
|---|---|---|---|
| `dm`（已有） | 人 + 1 个 Agent | 两者 | 人的消息唤醒 Agent |
| `group` | 人 + 1–16 个 Agent，由人管理成员 | 成员 | 人或 Agent 的消息只唤醒被 @ 的 Agent 成员；`@all` 唤醒全部 Agent 成员 |
| `agent_dm` | 2 个 Agent；人只能看 | 两个 Agent | 消息唤醒对方 |

- 群成员资格只授予群内通信的权限，不会顺带建立 Agent 之间的私聊权限。
- 成员变更后立即生效：被移出的 Agent 不能再读写该群，已排队的投递也会取消。
- 新加入的成员能读到以前的历史，但这些历史不会作为新任务重放。
- 删除 Agent 时：它在群里发过的消息保留，作者名用当时的快照；它的成员资格和排队中的投递一并删除。

## 3. 防刷屏

- **会话链预算**：每条消息都属于一条会话链。
  - 人发的消息开启一条新链，预算 32 条 Agent 发布。
  - 只由 Agent 消息触发的回合，开启一条新的 Agent 链，预算 8 条。
  - 跨频道、群和私聊互相分叉时，预算不会重置。模型也不能自己指定或重置链。
- **超出预算时**：链进入「暂停」状态，后续发布被拒绝，并在相关频道发一条系统消息：「已暂停，请人回复后继续」。这对应 plan 的「往返超过 6 次自动暂停并通知人」，8 条大约等于 4 个来回。
- **频率上限**：每个 Agent 每小时最多 60 条消息，超出时 `send_message` 返回错误说明。
- **系统提示词约束**：不发空洞的确认或感谢；群里没被问到、也没有要补充的内容时保持沉默；共同的工作放到群里，单独的任务用私聊。

## 4. 调度

- 保持现有机制：每个 Agent 同时只有一个活跃回合，全局最多 3 个。
- **新增防抖**：同一 Agent 的新消息到达后静默 1.5 秒，期间来的消息合并成一个回合。
- **新增排队可见性**：`agent.state` 增加两个字段：
  - 排队位置；
  - 等待原因：全局并发满了，或者在等工作站写租约。

  前端在聊天里显示「Ada 排在第 2 位」「Bob 正在等 Bench 1」。
- **队列上限**：每个 Agent 最多 8 个未完成的投递，全局最多 64 个；超出时拒绝并给出提示。只由 Agent 触发的回合，排队超过 5 分钟就放弃。
- **重启语义不变**：进行中的回合标为中断、不重放；排队中的回合继续调度。

## 6. 数据库变更（迁移 0002）

- `channels`：
  - `kind` 增加 `group`、`agent_dm`；新增 `title`。
  - `dm_key` 也用于 `agent_dm`，值为两个 Agent ID 排序后拼接。
  - SQLite 改约束需要重建表，由 drizzle 生成迁移。
- `messages`：新增 `reply_to_id`、`chain_id`、`mentions`（JSON）、`author_name`（快照）。
- 新增 `chains`：`id, org_id, origin_kind, origin_message_id, budget, used, paused_at, created_at`。
- 新增 `reactions`：`message_id, actor_kind, actor_id, emoji, created_at`，主键是前四列。
- 新增 `messages_fts`：FTS5 trigram 索引，由触发器维护。

## 7. 前端

- **聊天侧栏分三组**：群聊、私聊、Agent 间会话（只读）。可以新建群（填名字、选成员）和编辑群（改名、增删成员、输入群名确认后删除）。
- **群聊对话**：
  - 消息显示作者头像、名字、时间；同一作者 5 分钟内的消息合并显示；
  - 支持回复引用和反应 chips；
  - 输入框支持 `@` 自动补全；
  - 底部提示谁在工作、排第几、在等什么。
- **Agent 间会话**：只读，显示两个 Agent 的头像和各自的配色。
- **Portal 搜索（⌘/Ctrl+K）**：搜 Agent、频道、消息、工作站，点结果直接跳到消息位置。
- **活动检查器**：显示每个回合的触发来源（谁在哪个频道发的消息）和所属会话链。

## 8. 测试计划

1. **单元测试**：
   - 提及解析（`@名字`、`@all`、名字里带空格、中文名）；
   - 唤醒规则；会话链预算与暂停；频率上限；防抖合并；
   - 反应的幂等性；FTS 搜索（含中文和不足 3 个字符的词）。
2. **权限测试**：
   - 非成员不能读、写、搜索、反应；
   - 被移出群后立即失效；
   - Agent 消息触发的回合不能发到人和 Agent 的私聊；
   - 人在界面上不能以 Agent 身份发言或反应。
3. **多 Agent 集成测试**（用 ScriptedRuntime）：
   - 两个 Agent 在群里各做各的任务，同时第三个 Agent 的私聊不受阻塞；
   - 两个 Agent 讨论后得出结论；
   - Agent 之间循环发消息时，在第 8 条处暂停并通知人；
   - 重启后不重放。
4. **E2E**：建群、@ 唤醒、回复与反应、Agent 间会话只读、⌘K 搜索跳转、375 宽布局。
5. **验收**（plan 第 12 节，真实模型）：
   - 群里两个 dev Agent 各自完成 hive-sandbox 的一个小任务，期间私聊第三个 Agent 不受影响；
   - 两个 Agent 讨论并给出结论；
   - 故意让它们循环对话，确认会暂停并通知；
   - 预计花费不到 $0.5。
