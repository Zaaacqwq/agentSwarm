## 真实模型验收

模型用 qwen3.8-omni-flash。共 **10 个运行，用时 15.6 分钟（936 秒），总花费 $0.10**。根节点预算是 $2，实际用了 5%。

```
Lead (tech lead)            24 轮  $0.0413  → PR #1
├─ sum (developer)          10 轮  $0.0032  评审通过，已合并
├─ range (developer)        15 轮  $0.0069  第一次评审要求修改 → 修改 → 第二次评审通过，已合并
├─ strings (developer lead) 19 轮  $0.0134  评审通过，已合并
│  ├─ title-case            9 轮  $0.0047  评审通过，合并进 strings
│  └─ title-case-review     8 轮  $0.0035
├─ sum-review               7 轮  $0.0028
├─ range-review ×2         13+12 轮 $0.0192
└─ strings-review           8 轮  $0.0050
```

过程：
1. Lead 在 80 秒内派出了 3 个 dev，然后进入等待并让出工作站。3 个 dev 在 3 个工作站上并行开发。
2. strings 先写好 capitalize 并推送，然后派出 title-case。title-case 的分支从 strings 推送后的分支切出，所以能直接 import 刚写好的模块。
3. strings 先请 reviewer 评审 title-case，通过后合并，再推送、报告。
4. Lead 被唤醒后，同时为 3 个 dev 发起评审，3 个 reviewer 并行运行。
5. **评审抓到了一个真问题**：range 第一版遇到非数字参数会无限循环，例如 `range("a","f")` 会卡死并持续吃内存。reviewer 在子进程里加了 4 秒超时，复现出了这个问题。Lead 用 `message_agent` 把具体修改意见发回给 range；range 修改并补了回归测试，第二次评审才通过。整个过程完全按设计进行：range 收到修改要求后，之前的评审结论自动作废，必须重新评审才能合并。
6. Lead 依次合并、跑测试、推送，然后开 PR。

几处值得记录的细节：
- 第一个 range-review 用了约 6 分钟，原因是它反复在子进程里复现死循环，每次都要等超时。
- 两个负责字符串的 Agent 发现 Lead 在需求里写错了两个预期结果，例如 `"hELLo woRLD"` → `"HELLo WORLD"` 和"只把首字母大写"的规则矛盾。它们按正确的行为写了测试，并在报告里指出是需求写错了，没有为了迎合需求去改代码或削弱测试。Lead 在最终报告里也承认是自己的需求写错了。
- 仓库里原本埋好的 4 个失败测试（clamp、median、slugify、word-count）一个都没碰。reviewer 还确认了这 4 个失败在 `main` 上和在新分支上完全一样。

## 测试

- `npm test`：42 项全部通过。其中树相关的集成测试有 9 项，用 Pi 的假模型，按 Agent 名字分别编排回复：
  - lead 拆分任务 → 等待（只有 1 个运行名额时也不会死锁）→ 评审 → 合并 → 开一个 PR；
  - 孙 Agent 从父节点推送后的分支切出，再逐级合并回去；
  - 评审打回时不能合并；
  - 合并冲突会报出冲突文件，worktree 保持干净；
  - 取消根节点会连带取消整棵树，并释放所有工作站；
  - 层数、数量、预算上限；
  - 并行派生不会超出预算，也不会出现同名分支；
  - 子节点通过评审后又被要求修改时，之前的批准失效；
  - 取消子节点会唤醒正在等待的父节点；父节点在子节点没结束前不能交差。
- ws-exec 新增 3 项测试：
  - 合并必须指定评审过的那个提交，冲突时会中止合并；
  - 同一工作站上的另一个 worktree、它的 HOME、它的临时目录，都读写不到；
  - 在别的运行的 `~/.gitconfig` 里埋东西无效。
- `npm run e2e`：1 项通过。面板上的流程是：Dev 派 Helper 去修 bug → 评审 → 合并 → 开 PR；能看到 Agent 树、评审结论、合并标记和 PR 链接，点进 Helper 能看到它自己的时间线。
- `npm run check`：真机 24/24 通过。新增的一项是"同一工作站上另一个运行的 worktree 读不到"。
- 迁移 0001 和 0002 只新增字段；swarmd 启动时会自动备份数据库（`agentswarm.db.backup-2026-10-17T02-58-33…`）。

## 代码审查

code-reviewer 报了 0 个 CRITICAL、4 个 HIGH、7 个 MEDIUM、4 个 LOW。4 个 HIGH 都已修复，并且都有回归测试：
1. **同一工作站上的运行能写对方的 worktree**，可以借此绕过评审。现在沙箱只放行这个运行自己的 worktree，每个运行也有自己独立的 HOME 和临时目录。
2. **并行派生会突破预算、数量上限，还可能出现同名分支**。现在检查和写入在一个事务里完成，并加了"任务分支唯一"的部分唯一索引；树相关的工具改为依次执行。
3. **评审没有和具体提交绑定**。现在评审时记下当时的提交，合并只合这一个提交，并要求子节点处于成功状态；子节点被要求修改后，之前的评审和合并状态作废；结果消息里只显示这一次评审的结论。
4. **父节点恢复后没有被调度**。现在恢复排队后会立即调度，调度过程中又有任务入队时会再跑一轮，取消后也会调度。

MEDIUM 全部修复：
- 等待中收到的消息先攒着，等恢复时一起送达；
- 父节点被取消后不能再派生子节点；
- 子节点没结束时，父节点不能结束；
- 多次评审时等待列表是累加，而不是覆盖；
- 子 Agent 写的文字都用"不可信数据"的标记包起来，提示词里也写明这一点；
- 已结束子节点没花完的预算会还给父节点，给已结束的子节点发消息时会自动补充预算。

LOW 全部修复：节点名过长时截断，合并时忽略未跟踪的文件，开 PR 前做检查，`message_agent` 只能发给任务类的子节点。

## 开发中发现并修复的问题

- **安装脚本漏装文件**：安装脚本里 ws-exec 的文件清单是写死的，漏掉了新加的 `space.ts`，导致装上的 ws-exec 无法启动。现在改为复制全部源文件，并在替换前先试运行一次。
- **预算规则**：最初每派生一个子节点就把剩余额度对半分，reviewer 分到的预算会把父节点自己的额度压到 0。现在父节点保留 15%，子任务默认分剩余额度的 30%。
- **分支命名**：git 不允许 `a` 和 `a/b` 两个分支同时存在，所以改用"每棵树一个目录、节点平铺、用 `--` 表示层级"的写法（R2 方案第 1 节）。

## 剩余问题（留到 R3 及以后）

- **worktree 越积越多**：树结束后，各工作站上的 worktree 不会被删除，会一直占用 SwarmWS 卷的空间。应该在 PR 合并或关闭后清理。
- **子分支越积越多**：GitHub 上的 `swarm/…` 子分支同样会累积，应该在 PR 合并后删除。
- **一次性 Agent 的记录越积越多**：数据库里一次性 Agent 的记录会一直增加，面板不显示它们，但应该定期清理。
- **PR 正文由 Agent 撰写**：只能作为参考，以你在 GitHub 上看到的 diff 为准。合并始终只能由你来做。
- **评审结论只是参考**：被评审的子 Agent 理论上可以在报告或代码里写东西去影响 reviewer（报告和 diff 已经标记为不可信数据）。最终的把关仍然是你合并 PR 这一步。
