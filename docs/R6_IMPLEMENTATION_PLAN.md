## 0. 本阶段解决什么

现在 Agent 只能读写代码、跑命令，**看不见也点不了**界面。R5 验收时：
- ZAA-5 改的是 Fridgy 的 Swift 代码，可沙箱里的 `xcodebuild` 加载不了 Swift 宏，Agent 连编译都过不了；
- 改完对不对只能靠评审读 diff，最后由你在 Xcode 里自己试。

本阶段做完后：
- **iOS 项目**：dev 能在沙箱里编译、跑单元测试；QA 在模拟器里装上 App，按验收标准点一遍主要流程，每一步截图；
- **网页项目**：QA 启动开发服务器，用无头浏览器打开、点击、填表、截图；
- **验收报告带截图**，跟着 PR 一起提交，在手机上的 GitHub 和 Linear 里都能看到；
- 截图交给支持图片的模型去看，需要时放大局部。

你的 Apple 项目（Fridgy、Cents、DoFocus、vibeIsland）从这一阶段起可以由 Agent 自己验证。合并前装到你手机上试，靠的是 PLAN.md 第 17 节的 Xcode Cloud，不在本阶段。

## 1. 验收（真实环境）

1. **Fridgy 的一张 UI ticket**（例如改一个页面的文案或布局），走完整流程：
   - dev 在沙箱里编译通过，单元测试通过；
   - QA 在模拟器里装上 App，按验收标准点一遍，每一步截图；
   - PR 里的 `acceptance.md` 带截图，ticket 里有链接。
2. **betterUWWorks 的一张网页 ticket**：
   - QA 在 3100 端口启动开发服务器，用浏览器验证改动，截图进验收报告；
   - 全程不碰线上服务。
3. **两件事同时进行**：两个重任务各占一个工作站，互不干扰；内存紧张时新的重任务排队，不会被系统杀掉。
4. **隔离**：
   - 一个工作站的 Agent 操作不了别的工作站的模拟器和浏览器；
   - 截不到你的屏幕；
   - 浏览器打不开内网地址，也打不开你的服务，只有项目自己的开发服务器例外；
   - 模拟器里没有上一个项目留下的数据。
5. **费用和用时**：识图请求有超时和重试；每张 ticket 的识图费用在面板里单独列出。

## 2. 今天已经实测的

| 项目 | 结果 |
|---|---|
| Swift 宏在 seatbelt 里 | **原因找到了**：`swiftc` 运行宏插件时自己会再套一层沙箱，和 Codex 一样，在沙箱里再开沙箱会失败。`@Observable` 在 seatbelt 里编译报错，加 `-disable-sandbox` 后通过 |
| 模拟器在工作站的沙箱里（ws-8，经 ws-launch，套着现有 seatbelt） | 列出运行时、建设备、启动都可以，冷启动 35 秒；打开"设置"App 成功 |
| 模拟器截图（同上） | **失败**：`simctl io screenshot` 保存文件时报 Operation not permitted，换成输出到标准输出也一样。在你的账号下套同样的 seatbelt 规则截图正常，说明问题出在工作站环境或文件规则上。【需实测】 |
| AXe（读界面、点击） | 工作站用不了：R0 时装在了你的家目录下（`~/.local/opt/axe`），工作站没有权限读取。要改装到公共目录 |
| 无头 Chromium 在 seatbelt 里 | 在你的账号下套 seatbelt 能启动、打开页面、读出内容，Chromium 自己的沙箱不受影响。工作站上【需实测】 |

测试用的模拟器设备都已删除。

## 3. 编译：让 Swift 宏能用

- 编译 Swift 时统一加上 `-disable-sandbox`，让 `swiftc` 不再自己套沙箱。外面已经有两道墙：独立的 macOS 用户和 seatbelt，所以安全性不降低。这和 R0 给 Codex 关掉自带沙箱是同一个道理。
- **做法**：沙箱里的 `PATH` 最前面放一个 `xcodebuild` 包装脚本，自动加上：
  - `OTHER_SWIFT_FLAGS='$(inherited) -disable-sandbox'`；
  - `-derivedDataPath`，放在这次运行自己的目录里；
  - 编译到模拟器时加 `CODE_SIGNING_ALLOWED=NO`。

  这样原生 Agent、Claude Code、Codex 直接敲 `xcodebuild` 就能用，不用记参数。`swift build` 和 `swift test` 也同样包装（SwiftPM 自带 `--disable-sandbox`）。
- **Swift 包**：解析 `Package.swift` 和运行包插件时也会套沙箱。【需实测】需要哪些 xcodebuild 选项，候选是 `-skipPackagePluginValidation`、`-skipMacroValidation`，以及关掉清单沙箱的设置。Fridgy 依赖 Supabase 的 Swift 包，正好用来测。
- 项目档案（R5）里增加 iOS 设置：工程或 workspace、scheme、默认模拟器型号。不填的话 Agent 自己用 `xcodebuild -list` 找。
- Fridgy 的 `Config.local.xcconfig` 这类文件，用 R5 的"本地配置文件"上传，编译时自动放进 worktree。

## 4. 模拟器

### 4.1 设备
- 每个工作站有自己的一台模拟器设备（R0 已确认各工作站的设备互相隔离），名字是 `agentswarm-ws-N`，默认 iPhone 17 和最新 iOS，项目档案可以改。
- 一次运行里，设备启动后一直开着；运行结束后关机，并在后台抹掉数据（`simctl erase`），下一个项目拿到的是干净的设备。
- 冷启动约 35 秒，所以设备只在运行第一次用到时才启动。

### 4.2 工具（给原生 Agent）

| 工具 | 作用 |
|---|---|
| `sim_build({scheme?, configuration?})` | 编译并装到这个工作站的模拟器上，返回编译错误的摘要 |
| `sim_launch({bundle_id?, args?})` | 启动 App；可以带启动参数，用于跳过登录、加载测试数据等 |
| `sim_ui()` | 读当前界面结构（AXe `describe-ui`），每个元素一个编号，带标签和位置 |
| `sim_tap({element} 或 {x, y})` | 点击，用 AXe 的 `physical` 方式（R0：默认方式在 Xcode 27 上无效）；可以按编号，也可以按坐标 |
| `sim_type({text})`、`sim_swipe({from, to})`、`sim_button({name})` | 输入文字、滑动、按 Home 等实体按键 |
| `sim_screenshot()` | 截图，以图片形式交给模型（见第 6 节） |
| `sim_logs({since?})` | App 最近的日志，例如崩溃时看原因 |

- 这些工具都是 ws-exec 里参数固定的操作，按"这个工作站的设备"执行，请求里不能指定别的设备。
- Claude Code 和 Codex 用 `ws_bash` 里同样的命令行（`simctl`、`axe`）。CLI 的 shell 命令本来就套着同一层沙箱。

### 4.3 截图失败的处理【需实测】
按顺序试，选第一个可行的：
1. 找出是哪条文件规则挡住了，在 seatbelt 里放行截图实际写入的那个位置；
2. 改用 AXe 截图；
3. 截图这一个操作不套 seatbelt：参数固定、输出路径由 ws-exec 决定，仍以工作站用户的身份运行（第一道墙还在）。

### 4.4 安装
AXe 改装到 `/usr/local/libexec/agentswarm/tools/`，和 R4 安装 CLI 的做法一样：
- 核对固定的 SHA-256 和开发者签名；
- 由你运行 `sudo zsh scripts/setup.sh --update-tools` 安装。

## 5. 浏览器

### 5.1 运行方式
- 每次运行用自己的无头 Chromium（Playwright 的 headless shell），跑在工作站用户和 seatbelt 里，用户数据目录在这次运行自己的目录下。
- 浏览器放在一个 ws-exec 长连接会话里：swarmd 和它通过标准输入输出按行交换命令和结果，用 `--remote-debugging-pipe`，**不开调试端口**，别的工作站连不上。
- Chromium 和 Playwright 的版本固定，由 `setup.sh --update-tools` 装到公共目录，工作站只读。

### 5.2 工具

| 工具 | 作用 |
|---|---|
| `browser_open({url})` | 打开网址 |
| `browser_snapshot()` | 读页面结构（无障碍树），每个元素一个编号 |
| `browser_click({element})`、`browser_fill({element, text})`、`browser_press({key})` | 点击、填写、按键 |
| `browser_screenshot({full_page?})` | 截图，交给模型 |
| `browser_console()` | 控制台报错和失败的网络请求 |

### 5.3 能访问哪里（推荐，见第 10 节第 2 条）
- **可以操作（点击、填写、提交）**：
  - 本机的开发服务器，也就是 `localhost` 或 `127.0.0.1` 上不在端口禁止名单里的端口；
  - 项目档案里列出的测试地址。
- **只能看（打开、读、截图）**：其他公网网站。
- **不能访问**：
  - 内网和 tailnet 地址（`10/8`、`172.16/12`、`192.168/16`、`100.64/10`、`fd00::/8` 等）；
  - 名单里的端口和 swarmd 的端口。

  每个请求先解析域名再检查 IP，防止 DNS 重绑定。
- 网页上的文字一律当数据，不当指令（沿用安全底线）。

## 6. 识图和局部放大

- 截图缩到最长边 1000 像素再交给模型，节省费用。上下文里只保留最新 3 张，旧的换成一行"已移除的截图：第几步，看到了什么"。
- `look_at({region})`：放大最新截图里的一块区域（比例坐标 0–1000）。R0 发现小图标容易看错，放大后再判断。
- 请求超时 60 秒，失败重试一次。R0 遇到过 148 秒和 333 秒的延迟尖峰。
- **有界面结构时以结构为准**：点击用 `sim_ui` 或 `browser_snapshot` 给出的元素编号，识图用来确认"看起来对不对"。没有结构时（自绘界面、游戏）才按识图给的坐标点击。
- 模型的坐标回答兼容几种常见写法（R0 遇到过 `point_2d`、缺引号）。
- 需要看图的角色（QA，以及要看界面的 dev）用支持图片的模型。现在默认的 qwen3.8-omni-flash 就支持；如果某个角色换成了不支持图片的模型，派生时提示。

## 7. QA 流程和截图留痕

- QA 的工作说明里写明：
  - 按方案里的验收标准逐条操作；
  - 每条都截图，并写下"做了什么、看到了什么、是否符合"。
- 截图转成 JPEG（每张约 100 KB），放进 `docs/agentswarm/<任务>/screenshots/`，和 `acceptance.md` 一起提交。验收报告里直接引用图片，GitHub 的 PR 页面上就能看到，包括手机。
- 每张 ticket 最多 20 张截图（推荐，见第 10 节第 3 条）。
- 面板的实时动态里，截图显示为缩略图，点开看大图。
- 本地项目（沙盒实验）的截图同样放在本机仓库里，用 R5 的 `blob` 链接查看。

## 8. 资源：重任务槽

- 派生子 Agent 时增加 `needs: ["simulator" | "browser"]`。带 `needs` 的子 Agent 占一个**重任务槽**，最多 2 个，可在设置里调。
- 开始重任务前检查内存压力。系统内存紧张时，新的重任务排队，已经在跑的不受影响。
- 模拟器和浏览器在运行结束、取消或超时时都会关掉，运行结束的清理步骤里统一处理。
- 面板的"This Mac"一节显示重任务槽的占用和内存压力。

## 9. 安全

- 新增的操作都在 ws-exec 里，参数固定，只作用于这个工作站自己的设备和浏览器。swarmd 只在派生时根据 `needs` 开放对应的工具。
- seatbelt 现有的禁止规则不变：剪贴板、WindowServer、Apple Events、你的家目录、其他工作站。第 4.3 节如果要放行，只放行截图那一处。
- 模拟器每次运行后抹掉数据，浏览器每次运行用新的用户数据目录，项目之间不会互相看到登录状态和数据。
- 截图提交前也走 Relay 的检查。R5 的规则是推送内容里不能出现本地配置文件中的值；截图是图片，查不了里面的文字。所以 QA 的工作说明里写明：截图前不要让页面显示密钥。

## 10. 需要你决定的

1. **桌面会话（操作 Mac 原生 App）移出 R6。**（推荐）
   - PLAN.md 原本把"桌面会话改进"放在 R6，但重写后还没有桌面功能。它需要你批准会话、设禁区、截你的屏幕，风险和工作量都比模拟器、浏览器大得多。
   - 你的项目里 iOS 占多数，模拟器先做完收益最大。
   - 推荐单独作为一个阶段，排在 R7 之后。
2. **浏览器能操作哪些网站。** 推荐第 5.3 节的规则：只操作本机开发服务器和项目档案里列出的测试地址，其他网站只能看。
3. **截图放在哪里。** 推荐提交进项目仓库（JPEG，每张 ticket 最多 20 张），好处是在手机上的 GitHub 里直接能看。另一个选择是只存在 swarmd 里、在面板上看，不占仓库空间，但离开 tailnet 就看不到。
4. **验收用的两张 ticket。** 推荐 Fridgy 的一张 UI 小改动和 betterUWWorks 的一张网页小改动，由你在 Linear 里交出。这次给 bug 打上 bug 标签，顺便补上 R5 没在真实环境里走过的快速流程。

## 11. 实现顺序和测试

1. **实测：**
   - 截图失败的原因（第 4.3 节）；
   - Swift 包的选项（第 3 节）；
   - 在工作站上编译 Fridgy；
   - 工作站上的 Chromium；
   - 两个模拟器同时运行时的内存占用。
2. **安装**：`setup.sh --update-tools` 安装 AXe、Chromium 和 Playwright，核对哈希和签名，并检查工作站能不能运行它们。
3. **编译**：`xcodebuild`、`swift` 的包装脚本，项目档案里的 iOS 设置。
4. **模拟器**：ws-exec 的模拟器操作，设备的创建、启动、关机和抹掉，`sim_*` 工具。
5. **浏览器**：ws-exec 长连接会话、访问规则、`browser_*` 工具。
6. **识图**：图片结果、上下文里只留最新几张、`look_at`、超时重试。
7. **QA 和留痕**：工作说明、截图转换和提交、验收报告模板、面板缩略图。
8. **重任务槽和内存压力**，以及清理。
9. **测试：**
   - 单元测试：坐标解析、访问规则（包括 DNS 重绑定）、上下文里旧截图的替换、包装脚本加的参数；
   - ws-exec 测试，使用真实的 seatbelt：
     - 宏编译通过；
     - 模拟器操作只作用于本工作站的设备；
     - 浏览器连不上内网地址和名单里的端口；
     - 没有调试端口；
   - 集成测试：用假模拟器和假浏览器，跑通 QA 从操作到截图、提交、验收报告；重任务排队；
   - E2E：实时动态里的截图缩略图；
   - 真实验收：第 1 节；
   - code-reviewer 和 security-reviewer 审查，因为新增了浏览器访问和放宽了编译沙箱。

不在本阶段：
